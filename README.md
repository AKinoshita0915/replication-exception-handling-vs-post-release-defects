# Overview and Motivation
Our final project will replicate Research Question 2 from the study “Studying the Relationship between Exception Handling Practices and Post-release Defects”: Do exception-handling anti-patterns contribute to a better explanation of the probability of post-release defects? To investigate this question, we have selected a real-world Java project from the Defects4J benchmark that contains identifiable exception-handling practices and traceable post-release defects [5]. We will analyze selected defects by examining the buggy and fixed code versions, identifying exception-handling anti-patterns, and investigating their relationship to the occurrence and resolution of post-release defects.
Software systems continuously evolve after their initial development as developers fix defects, add new functionality, improve performance, and adapt the system to changing requirements. As software evolves, effective maintenance becomes increasingly important because developers must understand existing code, diagnose failures, implement changes, and ensure that fixes do not introduce additional problems. Poorly designed code can make these activities more difficult and increase the cost and effort required to maintain the system.
Exception handling is an important aspect of software reliability and maintainability because it determines how a system responds to unexpected conditions and failures. Inappropriately designed exception-handling code can hide failures, lose diagnostic information, propagate errors incorrectly, or allow a program to continue operating in an unexpected state. Common exception-handling anti-patterns include swallowed exceptions, empty catch blocks, overly broad exception handling, exception masking, and improper exception propagation. Although such practices may sometimes appear to simplify error handling, they can make defects harder to detect, diagnose, and repair.
The motivation for this project is to investigate whether and how exception-handling anti-patterns are associated with real post-release software defects and how these practices change during software maintenance. Instead of studying artificially created examples, this project will examine real historical defects from the Google Gson project available in the Defects4J benchmark. Defects4J provides reproducible software defects together with buggy and fixed versions and associated tests, making it possible to study the evolution of the same code before and after a maintenance fix.
The project will replicate the defect-analysis process using the Gson project and extend it by systematically analyzing exception-handling practices in selected post-release defects. The buggy and fixed versions will be compared to identify exception-handling anti-patterns, determine their relationship to the observed defects, and examine how developers modified or removed these anti-patterns as part of the fixing process. The study will also consider maintenance-related factors such as debugging difficulty, fault localization, code modifications, exception propagation, and testing changes.
This problem is directly relevant to Software Maintenance and Evolution because exception-handling decisions made during software development can influence the effort required to diagnose and modify software throughout its lifetime. Understanding the connection between exception-handling anti-patterns and post-release defects can provide insight into how code-level design practices affect maintainability and the evolution of software. By combining reproducible defect analysis, source-code examination, and buggy-versus-fixed version comparison, this project aims to provide empirical evidence about the role of exception-handling anti-patterns in the maintenance of an evolving software system.
